Pipeline · command line

Org-to-Org Data Migration

Move data between two Salesforce orgs and prove, field by field, that it arrived intact.

What it does

  • Preflight compares both orgs and lists blocking issues before anything is written: missing fields, picklist values the target rejects, unmatched users, audit fields it cannot set.
  • Works out the load order from org metadata. Parents load first, and lookups that form loops (Account.ParentId, Account ↔ Contact) are filled in a second pass.
  • Rewrites every Id to its new value in the target, including owners and polymorphic fields such as Task.WhatId.
  • Validates twice: record counts, then every field of every record. A trigger that quietly changes data in the target gets caught.
  • Reruns send only what failed. Rollback removes every migrated record.

Run it

$ python migrate.py -c config.yaml preflight
$ python migrate.py -c config.yaml run
You get
One HTML sign-off report, plus CSVs for load errors, mismatches and data loss
Needs
Python 3 · simple-salesforce · DuckDB · Bulk API 2.0
Good to know
Current scope is Salesforce to Salesforce with the same data model. Files and attachments, Chatter and Person Accounts are not covered yet. The demo runs on two simulated orgs.

Local web app

Debug Log Analyzer

Find the one line that matters in a 20 MB debug log, and the failing API call among hundreds.

What it does

  • Pulls Apex debug logs by time range, user, status or API path such as /services/apexrest/orders.
  • Puts the real error first: unhandled and caught exceptions, failed validation rules, Flow errors, System.debug ERROR lines and HTTP callouts that returned 400 or above.
  • Adds a plain-English hint for common errors, the stack trace, and the events just before the failure.
  • Warns about governor limits at 80% or more and about the same query or DML repeated in a loop.
  • Searches inside log bodies for a record Id or order number, and copies a summary for Jira or Slack.

Run it

$ python sf_log_analyzer.py --org myOrg
You get
Opens at http://127.0.0.1:8766 in your browser
Needs
Python 3 · requests · Salesforce CLI login
Good to know
The detail depends on your trace flag levels. Raw logs stay in memory on your machine; nothing is uploaded.

Field Usage Finder

See which fields on an object are dead weight before you clean up or migrate.

What it does

  • Ranks every field on an object from unused to heavily used.
  • Measures the data: what share of records hold a value in each field.
  • Finds the references: Apex, triggers, Flows, validation rules, reports, page layouts, LWC, Aura, Visualforce, formula fields and email templates.
  • Gives a plain verdict per field, such as “NOT USED anywhere” or “Only on page layouts (but empty)”.
  • Saves a CSV naming every class, Flow or report that references each field.

Run it

$ python field_usage.py Account --org myOrg
$ python field_usage.py Invoice__c --org myOrg --custom-only
You get
Colour-coded table in the terminal and a CSV for the audit trail
Needs
Python 3 · simple-salesforce · rich
Good to know
Reference tracking covers custom fields; standard fields need the --scan-apex text search. It cannot see managed packages, dynamic SOQL or outside integrations, so treat “not used” as “check before deleting”.

Command line · HTML report

Permission Diff

Answer “why can this user do that and the other one can’t?” in one command.

What it does

  • Compares two profiles, two permission sets, or one of each, side by side.
  • Covers object access, field access, system permissions, Apex classes, Visualforce pages, tabs, apps, custom permissions, flows and custom metadata.
  • Reads straight from the org, or from two retrieved metadata XML files with no org connection.
  • Report has category filters, search and a “differences only” switch.
  • Exports the differences as CSV for an audit or a change ticket.

Run it

$ python permission_diff.py "Sales User" "Sales Manager" --org myOrg
$ python permission_diff.py --list --org myOrg
You get
Self-contained HTML report that opens in your browser
Needs
Python 3 · simple-salesforce
Good to know
Record type visibility is compared only in metadata-file mode, because Salesforce does not expose it for profiles through queries.

Local web app

Object Cleaner

Get data storage back by bulk-deleting old records, with a preview before every delete.

What it does

  • One row per object, standard or custom: older than N days, owner, and any SOQL condition.
  • Preview shows how many records match before anything is deleted.
  • Deletes through Bulk API 2.0 in 100,000-record jobs, so millions of Tasks or EmailMessages are fine.
  • Optional hard delete skips the Recycle Bin. Failed records are listed with the reason.
  • A storage meter refreshes after each delete, and your rows are saved for the next run.

Run it

$ python sf_cleanup_app.py --org myOrg
You get
Opens at http://127.0.0.1:8765 in your browser
Needs
Python 3 · requests · Salesforce CLI login
Good to know
A row needs at least one filter, so a blank row can never wipe an object. Deleting a parent record also deletes its children, and hard deletes cannot be undone.

Apex Log Cleaner

Clear thousands of debug logs in one run instead of clicking through the Developer Console.

What it does

  • Counts first with --dry-run, so you see what would go.
  • Deletes everything, only logs older than N days, or only one user’s logs.
  • Runs ten deletes in parallel and prints progress as it goes.
  • Asks for confirmation unless you pass --yes, which makes it safe to schedule.
  • Reports how many were deleted and lists any that failed.

Run it

$ python delete_apex_logs.py --org myOrg --dry-run
$ python delete_apex_logs.py --org myOrg --older-than-days 7
You get
Progress and a final count in the terminal
Needs
Python 3 · requests
Good to know
Uses the Tooling API with your existing Salesforce CLI login or an access token.

How they fit into a project

Nothing to install in the org

The tools are Python scripts that call the standard Salesforce REST, Tooling and Bulk APIs. There is no managed package, no connected app and no change to your org’s metadata.

Your data stays with you

The two web apps listen only on 127.0.0.1. Logs, record Ids and migration data are held on the machine that runs the tool and go nowhere else.

Safe by default

Anything that deletes or writes has a dry run or preview, asks for confirmation, and reports failures with the reason Salesforce returned.
